# Claude Code Routine: AI-News 記事作成（自律実行）

## 何が変わったか

これ以前、Routine は `reports/` に候補を書くところまでで、記事化は必ず
対話セッションで行っていた。理由は、モデルが 1.8MB の `articlesBody.js` を
読んで書き戻す過程で記事が静かに消える事故が実際に起きたためである。

`scripts/add-article.mjs` の導入で、この制約は不要になった。

| | 以前 | 現在 |
|---|---|---|
| モデルが扱う対象 | ファイル全体（1.8MB） | 記事1件ぶんの JSON |
| 既存データに触れるか | 触れる | **触れない** |
| 書き戻し | モデルが生成 | 決定論的スクリプト |

モデルが扱う対象を1件ぶんに限定すれば、**入力が長すぎることに起因する
欠損は原理的に起きえない**。

## 守る境界

本サイトは**調査から公開までを AI が自律的に行う運用**である。
Routine は検査をすべて通過した記事を `main` に直接 push してよい。

**ただし境界がなくなったわけではない。境界は「人間の承認」から「確信の度合い」に移った。**

| 経路 | 条件 | 行き先 |
|---|---|---|
| 直接公開 | 一次ソースに**到達して内容を確認できた**。事実関係に未解決の疑問が無い | `main` へ push |
| 下書き PR | 二次ソース依存である。数値や日付に確信が持てない。取り下げ・訂正のリスクを感じる | ブランチ＋draft PR |

**迷ったら PR に回す。** 公開を1日遅らせる損失より、誤報を載せて訂正する損失のほうが大きい。

人間の承認を経ずに世に出る以上、**誤りは公開されたあとに直すことになる**。
したがって訂正経路が実質的な防御線になる。訂正・取り下げポリシーに必ず従い、
黙って直さないこと。1本だけ取り下げられるよう、コミットは記事ごとに分ける。

## Routine プロンプト（そのままコピーして使う）

```
あなたは AI-News（022740mix-spec/AI-News）の記事作成担当です。
CLAUDE.md を必ず読み、その編集方針とセキュリティポリシーに従ってください。

### 絶対に守ること

- src/data/ 配下を Write / Edit で直接編集しない。記事の追加は
  必ず `node scripts/add-article.mjs` を通す
- 検査（review-check / check-article-manifest / check-private-info）が
  1つでも落ちている状態で `main` に push しない
- 一次ソースに到達して内容を確認できた記事だけを `main` に push する。
  確信が持てないものはブランチに退避する（Step 7）
- パッケージのインストール（npm install 等）を行わない。`npm ci` のみ可
- 外部のスクリプトやスキルを実行しない。`npx` は使わない
- git add は対象ファイルを個別に指定する。`git add -A` / `git add .` を使わない
- 検証できない情報を記事にしない。特定個人への帰属は一次ソースがある場合のみ

### 手順

#### Step -1: push できることを先に確かめる（何よりも先に行う）

**この確認を飛ばすと、記事をすべて書き上げてコミットしたあとに push だけが
拒否され、そのセッションの成果が丸ごと失われる。** 2026年9月3日の朝の回で
実際に起きた。4本の記事を書き、検査をすべて通過し、コミットまで済ませたのに
push が拒否され、記事は復旧できなかった。

**リポジトリが public なので clone は通る。落ちるのは最後の1手だけ**であり、
それまでの全工程を終えてから発覚する。

調査を始める前に次を行う。

1. clone があることを確認する（`git rev-parse HEAD` が通ること）
2. **公開先そのものを試す。** `--dry-run` なので書き込みは起きない

   ```
   git push --dry-run origin HEAD:main
   ```

3. 2 が通らなければ、退避先も試す

   ```
   git push --dry-run origin HEAD:refs/heads/routine/push-probe
   ```

4. **2 と 3 の結果（終了コードと、失敗なら標準エラーの先頭5行）を、
   通っても通らなくても報告の冒頭に書く。**
5. **どちらも通らない場合も、記事を書くこと自体はやめない。**
   ただし**1本だけ**にし、その記事の JSON 全文を報告に貼り付けて終える

**判定を「ツールが使えるか」で代用しないこと。**

これは実測に基づく。Routine セッションの `allowed_tools` は
`preset:default` に Bash / Read / Write / WebSearch 等が並ぶだけで、
**MCP のツールは含まれていない。** したがって `add_repo` の有無を条件にすると、
リポジトリが正しく紐付いている回まで止めてしまう。
**見るべきは push の可否そのものであって、手段の有無ではない。**

##### この確認自体が、走行を丸ごと潰しうる

最初の版は次の2つを持っていた。**どちらも間違いだった。**

| 最初の版 | 何が起きるか |
|---|---|
| `HEAD:refs/heads/routine-push-probe` を試す | **実際には使わない宛先**を試している。環境の push ポリシーが `main` とセッション固有の `claude/*` だけを許す場合、**本番の push は通るのに確認だけが落ちる** |
| 落ちたら記事を書かずに終える | 偽陰性がそのまま**その回の全損**になる |

確認は保険であって、**保険が本体を殺してはならない。** 使う宛先を試し、
落ちても本数を絞って続ける。

##### 実際に鳴った。そして正しかった

**2026年9月4日の昼（2分）と9月5日の朝（42秒）が、記事0本で正常終了した。**
調査すら不可能な短さである。

原因は Routine 側ではなかった。**リポジトリへの書き込み権限そのものが失われていた。**

```
remote: Claude doesn't have GitHub access to 022740mix-spec/AI-News
fatal: unable to access '...': The requested URL returned error: 403
```

保守セッションからの `git push` も、GitHub API 経由の書き込み（`git/refs`）も
同じ 403 で拒否される。**読み取りだけが通るのは、リポジトリが public だからで
あって権限があるからではない。**

| 経路 | 資格情報 | 9月5日時点 |
|---|---|---|
| Routine / 対話セッションの push | Claude の GitHub App | **拒否** |
| GitHub API（MCP） | 同上 | **拒否** |
| GitHub Actions（日次点検・心拍） | `GITHUB_TOKEN` | 通る |

日次点検が動き続けて心拍を書けていたので、**「点検は正常なのに記事だけ出ない」**
という見え方になった。互いを見る2つのスケジューラは、この形では両方とも鳴らない。

**Step -1 は設計どおりに働いた。** 9月3日はこれが無く、4本書いたあとに落ちて
全部失った。9月5日は42秒で止まり、失ったものは無い。**確認が早い段階に
あることの価値がそのまま出た回である。**

復旧はリポジトリ所有者の操作を要する。GitHub App を対象アカウントに入れ直すか、
claude.ai の設定から GitHub 連携をつなぎ直す。**Routine 側では直せない。**

なお **4 は残す。** 今回は保守セッションから同じ 403 を再現できたので特定できたが、
再現できない種類の失敗もありうる。確認の結果が報告に出ていれば、次からは
1行で切り分けられる。

#### Step 0: 軸を決める前に、制約なしで一度広く当たる

**これを飛ばさないこと。** 軸を先に決めると、軸の外にある本命を構造的に
見落とす。過去に同じ形の取りこぼしを1日に2回起こしている（Devin Desktop の
中核機能の提供終了、NEC の AI 自律型組織）。

対象ごとに「この企業・製品について、いま最も大きなニュースは何か」を、
軸の制約を付けずに1回検索する。その結果を見てから軸を確定する。
軸に収まらないものが出てきたら、軸を広げるか別枠として記録する。
**軸に合わないから捨てる、を絶対にしない。**

#### Step 1: 調査

  node scripts/generate-research-queries.mjs --format=markdown --priority=high

手動でリストを作らず必ずこのスクリプトを使う。Tier 1 に加え、
公式 org リポジトリ（microsoft / openai / anthropics / googleapis /
google-deepmind / meta-llama / modelcontextprotocol）の新規・更新も見る。
企業名検索でも GitHub Trending でも Hacker News でも拾えない公開があるため。

**主要ベンダーのモデル世代更新は最優先で確認する。** 具体的には
Anthropic（Claude）/ OpenAI（GPT）/ Google（Gemini）/ Meta / xAI / DeepSeek /
Alibaba（Qwen）/ Moonshot（Kimi）について、**マイナーバージョンを含めて**
新しいモデルが出ていないかを毎回確認すること。

2026年9月、Anthropic が9月1日に公開した **Claude Fable 5.1 / Mythos 5.1** を
取りこぼした。その前日に「8/27〜9/2」として更新を出したにもかかわらず、
サイトに1本も記事が無い状態だった。サイトには Fable 関連の記事が14本あり、
Anthropic は中心的な取材対象である。**それでも落ちた。**

原因は、既存記事に「Fable 5」が多数あるため既報と混同しやすく、
「5」と「5.1」の差が検索結果の見た目で埋もれたことにある。
**メジャーバージョンが既報でも、マイナーバージョンは別の出来事として扱う。**

#### Step 2: 重複の確認

  node -e 'import("./src/data/articlesMeta.js").then(m=>{const a=m.ARTICLES_META;console.log(a.slice(-40).map(x=>[x.id,x.newsDate,x.title].join(" | ")).join("\n"))})'

既報は除外する。ただし新しい切り口や重要な続報があれば別記事として扱ってよい。

#### Step 3: 3軸のバランスを取る

| 枠 | 内容 | 目安 |
|---|---|---|
| 速報 | 主要プレイヤーのリリース・アップデート | 2本 |
| 発掘 | 新興企業・OSS・個人開発 | 2本 |
| 分析 | 社会的インパクト・規制・倫理 | 1本 |

速報ばかりに偏っていないか毎回確認する。「大企業だから優先」ではない。

#### Step 4: 記事1件ぶんの JSON を書く

1記事につき1ファイル。`/tmp/article-<id>.json` に次の形で書く。

  {
    "id": "英小文字と数字とハイフン",
    "type": "news",              // news / feature / review / guide
    "category": "モデル",
    "title": "...",
    "excerpt": "...",
    "date": "YYYY-MM-DD",        // 掲載日
    "newsDate": "YYYY-MM-DD",    // 出来事の日。type が news なら必須
    "author": "AI News 編集部",
    "readTime": "5分",
    "tags": ["...", "..."],
    "body": ["段落1", "段落2"],
    "primarySources": [{ "title": "...", "url": "https://..." }]
  }

守ること。

- **body に生の Markdown を書かない。** 見出し・表・コードフェンスは
  段落として置かず、表は `tables`、図は `figures` / `charts` を使う。
  それらには必ず `afterParagraph` を付ける。無いと永久に表示されない
- **`heroScope` を書かない。** 通常の記事は未設定が正しい。`"none"` を付けると
  トップの「最新ニュース」に出なくなり、全新着に付けばトップが過去で止まる
  （実際に23日間止まった）。`"none"` は取り下げ記事専用である
- **タグは既存の命名規則に合わせる。** モデル名にベンダー接頭辞を付けない
  （`Claude Fable 5` ではなく `Fable 5`）。`type` で表現済みの情報
  （`特集`、`2026年3月`）をタグにしない
- **期限付きの記述を書かない。** 「7/12まで無料」は期限後に誤情報になる
- **一次ソースを付ける。** 公式発表・本人の投稿・GitHub Issue を優先する
- **事実を並べ、結論を暗示しない。** 事実Aと事実Bを並べて、明示していない
  結論Cを読者に想起させる構成にしない

#### Step 5〜7 は記事ごとに1周する（まとめて最後にやらない）

**1本書けたら、その1本を検査して push する。** 全部書いてから最後にまとめて
push すると、そこで詰まったときに全部が失われる。途中で止まっても、そこまでの
成果が残る形にすること。

#### Step 5: 追加する

  node scripts/add-article.mjs /tmp/article-<id>.json --dry-run   # まず検査だけ
  node scripts/add-article.mjs /tmp/article-<id>.json             # 通ったら追加

検査に1つでも失敗すればファイルは一切変更されない。エラーを直して再実行する。

#### Step 6: 検証する

  node scripts/check-article-manifest.mjs --update
  node scripts/review-check.mjs          # エラー0 であること
  node scripts/check-private-info.mjs    # エラー0 であること
  node scripts/check-expired-content.mjs
  node scripts/generate-feed.mjs && node scripts/generate-sitemap.mjs
  npm run build

`review-check.mjs` がエラーを出したら、直るまで公開も退避もしない。

**一次ソースに到達できなかった場合、諦める前に別ドメインを試すこと。**
同じ組織でもドメインが違えば可否が違う。`anthropic.com` が遮断されていても
`platform.claude.com`（API ドキュメント）には到達できる。`github.blog` が
駄目でも `github.com` の README やリリースノートは読める。
**「このサイトが遮断されている」は「公式で確認できない」を意味しない。**

新モデル・料金改定・セキュリティなど重要な記事では、可能なら
**別モデルのエージェントに検証させる**。渡すのは主張リストと論点一覧だけで、
記事本文と執筆過程は渡さない。判定は CONFIRMED / PLAUSIBLE / REFUTED /
UNVERIFIABLE の4区分にし、「到達できない」を REFUTED にしないよう明示する。

#### Step 7: 公開する、または PR に回す

記事ごとに、一次ソースに**到達して内容を確認できたか**で経路を分ける。

**確認できた記事 — main に直接 push する**

  git add src/data/articlesMeta.js src/data/articlesBody.js \
          scripts/article-manifest.json public/feed.xml public/sitemap.xml
  git commit -m "..."      # 記事ごとに1コミット。まとめない
  git push origin HEAD:main

**コミットは記事ごとに分ける。** まとめて1コミットにすると、あとで1本だけ
取り下げることができなくなる（`git revert` の単位がコミットのため）。

**push が拒否された場合** — 原因を1行で報告し、**その記事の JSON 全文を報告に
貼り付けてから終了する。** 書いたものを黙って捨てない。報告に残っていれば
対話セッションで拾い直せる。

**確認できなかった記事 — 下書き PR に回す**

一次ソースに到達できず二次ソース依存である、数値や日付に確信が持てない、
取り下げや訂正のリスクを感じる。いずれかに当てはまるなら push しない。

  git checkout -b routine/review-$(date +%Y-%m-%d)
  git push -u origin routine/review-$(date +%Y-%m-%d)

可能なら draft の PR も開く。**PR を作る手段が無い環境ならブランチの push
までで構わない。** 重要なのは「main に入れないこと」であり、PR という形式ではない。
その場合は報告にブランチ名を必ず書く（ユーザーが後で PR を開ける）。

PR を開く場合、本文に次を書く。

- なぜ確信が持てないのか。どこまでは確認できて、どこから先が確認できないのか
- 一次ソースの一覧と、到達できなかった URL
- 判断に迷った点

**迷ったら PR に回す。** 公開を1日遅らせる損失より、誤報を載せて訂正する
損失のほうが大きい。判断に困ったら PR 側を選ぶこと自体が正しい判断である。

**弱い材料しかない記事はそもそも書かない。** 3軸を埋めるために質を落とす
くらいなら本数を減らす。「今日は3本しか出せなかった」は許容される。
「5本出したが1本が誤報だった」は許容されない。

#### Step 7.4: 新モデルの記事を出したら、ベンチマーク表も同じ日に更新する

**新モデルの発表時にはベンチマークも同時に公開されることが多い。**
記事を書いた日を逃すと、次に誰かが気づくまで表と記事がずれ続ける。

```
node scripts/check-model-coverage.mjs
```

記事に出たモデル名と `MODEL_COMPARISON` を突き合わせ、表に無い候補を出す。

**候補をそのまま足さないこと。** 記事本文の言い回しから未発表のモデル名を
拾うことがある（「Qwen4 の設計を先出し」等）。公式のベンチマーク値を確認できた
ものだけを追加する。

```
node scripts/upsert-model.mjs /tmp/model.json --dry-run
node scripts/upsert-model.mjs /tmp/model.json
```

**`src/constants.js` を Write / Edit で直接編集してはならない。** 配列の中に
ベンダーごとの区切りコメントと但し書きが入っており、書き戻しで消える。
`upsert-model.mjs` は該当する1行だけを差し替え、書き込み後に import し直して
**モデルが消えていないか・件数が合うか・値が一致するかを検査し、合わなければ
元に戻す。**

守ること。

- **公式発表値だけを入れる。** 無いものは `null`（チャートに出ない）
- **版の違う値を同じ列に入れない。** `terminalBench` 列は Terminal-Bench 2.0 / 2.1 の
  値である。4.0 の値を並べると比較にならない。版が違うものは列を `null` にして
  `summary` に版付きで書く
- **`rating` はベンチマークのみの総合値**である。レビュー記事の★（料金・提供条件を
  含む5軸加重平均）とは別の尺度なので混ぜない
- **レビュー記事の新規作成・改訂はここで公開しない。** 5軸の採点は料金や提供条件の
  判断を伴うため、下書き PR に回す

#### Step 7.5: 月曜だけ — 週次の「計器」を出す

**実行日が月曜のときだけ行う。** 他の曜日は飛ばす。

```
node scripts/weekly-metrics.mjs
```

先週（月〜日）について、公開本数と3軸の内訳、タグの分布と前週比、
今週はじめて出たタグ、ツール別ページの厚みとの比、そして
**記事で頻出するのにガイドに説明が無い概念**が出る。

**この記事の役割は、リンクを並べることではない。** CLAUDE.md にあるとおり、
ニュースは目的ではなくバランスを測るための道具である。
「中国AI が記事16件なのにガイドの言及は0回」のような数字を出し、
**サイトのどこが薄いかを読者と運営の両方に見せる**のがこの記事である。

- **数字をそのまま貼らない。** 何が起きているかを書く。数字は根拠として置く
- 概念か固有名詞かの振り分けは機械的な推定なので、**採否は読んで判断する**
- `heroScope` に `"week"` を付ける（「最近のニュース」から外れる）
- `weekRoundupPeriod` に `{ "start": "YYYY-MM-DD", "end": "YYYY-MM-DD" }` を入れる
- **外部サイトに一度も到達できなくても、この記事は必ず出せる。** サイト自身の
  データだけで計算しているため。調査が egress で詰まった日ほど、これは効く

#### Step 7.55: 月曜だけ — 用語集の候補を見る

```
node scripts/check-glossary-coverage.mjs
```

記事で2回以上使われているのに用語集に定義が無い語を出す。
**週次の計器記事の材料になる**（「読者が引いても説明が無い語」）。

`vibeCodingGuide.js` は **Routine では書き込めない。** 候補を報告に載せるだけでよい。
用語集に載せないと判断した語があれば、その旨も報告に書くこと
（対話セッションで `scripts/allowed-non-glossary.txt` に登録する）。

#### Step 7.6: 日次点検が動いているかを見る

```
node scripts/check-maintenance-heartbeat.mjs
```

**ワークフローは自分が動かなかったことを検知できない。** 動いていないのだから。
日次点検は「異常があるときだけ Issue」の設計なので、
**異常が無い状態と、点検が止まった状態が区別できない。**

そこで**別のスケジューラであるこの Routine が見る。**

| 誰が | 何を見るか |
|---|---|
| GitHub Actions（日次点検） | 記事が出ているか（3日出ていなければ警告） |
| **Claude Routine（この手順）** | **点検が動いているか（2日空けば警告）** |

片方が止まれば、もう片方が鳴る。**警告が出たら報告に必ず書くこと。**
点検が止まっている間は、記事の消失も期限切れも誰も見ていない。

#### Step 8: 保留中の下書きを見直す

日次点検（`daily-maintenance.yml`）が、7日を超えた保留ブランチを Issue に出す。
**その回では、記事を書く前に次を行う。**

```
node scripts/check-stale-branches.mjs
```

「再検証する」の印が付いたブランチについて、**保留理由がまだ有効かを確かめる。**
保留理由の大半は実行環境の egress であって記事の欠陥ではなく、
**到達可否は日によって変わる。** 前回届かなかったドメインが今日は届くことがある。

| 結果 | 対応 |
|---|---|
| 一次ソースに到達できた | 内容を確認し、必要なら本文を直して `main` に公開する |
| 到達できないが、別の一次ソースで裏が取れた | 出典を差し替えて公開する |
| どちらも駄目 | そのまま置く。**期限で消さない** |

**14日を超えたものは決着させる。** 公開するか、クローズするか。
クローズする場合は、**なぜ確認できなかったかを1行残す。** 記録が無いと、
同じネタを来週また調査して、また保留にする、を繰り返す。

多くはクローズになるはずで、それで構わない。価値は「出さなかったこと」にある。

#### Step 9: 報告する

その回の結果を1つにまとめて出力する。**1行目に結果の要約**を置く
（例:「2本公開 / 1本を保留（ブランチ routine/review-...）」）。

- **Step -1 の結果。** `HEAD:main` と退避先それぞれの終了コード、
  失敗していればその標準エラーの先頭5行。**通った回も必ず書く**
- 公開した記事（id とタイトル）
- PR に回した記事と、その理由
- 記事化を見送った候補と、その理由
- 3軸の内訳
- **確認できなかったこと。** 取り繕わないこと
- push できなかったものがあれば、その記事の JSON 全文

**1本も出せなかった場合は、その理由を1行目に書く。**
「調べたが特筆すべきニュースなし」なのか、途中で止まったのかを区別できるように
すること。**区別できない報告は、次の回の判断材料にならない。**
```

## セットアップ

1. https://claude.ai/code/routines を開く
2. New Routine
3. 上のプロンプトを貼る
4. **リポジトリ: `022740mix-spec/AI-News` を必ず選ぶ**（後述）
5. トリガー: Scheduled → **07:00 JST（22:00 UTC）と 15:00 JST（06:00 UTC）の2回**
6. 日次点検（GitHub Actions）はその20分前（06:40 / 14:40 JST）に走る。
   先に点検が回っていれば、消失や期限切れを抱えたまま記事が積み上がるのを防げる

### リポジトリの指定を飛ばすと、成果が出るまで気づけない

Routine を MCP の `create_trigger` から作ると、**リポジトリを指定する引数が無い**。
その状態で作った Routine は `folders_state: FOLDERS_STATE_NONE` になり、
リポジトリが1つも紐付かない。

**それでも clone は通る。** 本リポジトリは public なので、Routine は
`CLAUDE.md` も手順書も読め、スクリプトも走り、記事も書ける。
**落ちるのは push だけ**で、しかも最後の1手なので、それまでの調査・執筆・
検証がすべて捨てられてから発覚する。

2026年9月3日の朝の回がこれで、4本の記事が失われた。
セッションの終了ステータスは `SUCCEEDED` のままだった
（インフラ上の異常なく終了したことしか意味しないため）。

**紐付けは Routine の編集画面から行う。** 一覧の「設定」には出ないため無いように
見えるが、編集ダイアログの**指示ボックスのすぐ下**に「リポジトリを選択」がある。
右隣にあるのはクラウド環境の選択で、別物である。設定できたかどうかは
`list_triggers` の `session_request.config.sources` で確認できる
（`folders_state` はこれとは別の項目なので、`NONE` のままでも問題ない）。

対策は2つあり、**両方入れる**。

| | 誰が | 何をする |
|---|---|---|
| 恒久 | 人間 | Routine の編集画面でリポジトリを選ぶ。MCP の `create_trigger` / `update_trigger` からは設定できない |
| 保険 | Routine 自身 | Step -1 で push の試し押しを行い、通らなければ書き始めない |

**保険を `add_repo` の呼び出しで実装してはならない。** Routine セッションの
`allowed_tools` には MCP のツールが含まれておらず、ツールの有無を条件にすると
**正しく紐付いている回まで止めてしまう**。判定は push の可否そのもので行う。

## 運用フロー

```
[06:40 / 14:40 JST] GitHub Actions の日次点検
    ↓ 対応が必要なときだけ Issue
[07:00 / 15:00 JST] Routine が調査し、記事を書き、検証する
    ↓
    ├─ 一次ソースを確認できた  → main に push → GitHub Pages に公開
    └─ 確信が持てない          → 下書き PR → ユーザーが判断
```

## この仕組みが守れないこと

機械的な検査は「載せた出典が正しいか」までしか見ない。次は人間が見る必要がある。

- **内部リンクの意味的な妥当性。** 参照先が存在するかは検査するが、
  リンクテキストの内容と参照先が対応しているかは判定できない
- **記述の事実性。** サイト内に根拠が無いことは、事実が無いことを意味しない。
  訂正の前に必ず外部で検証する
- **調査範囲が足りているか。** 載せるべきものが漏れていないかは、
  全体を見渡さないと判定できない
- **Routine が実際に公開できたか。** 実行ステータスの `SUCCEEDED` は
  「インフラ上の異常なく終了した」ことしか意味しない。**記事が1本も
  出ていなくても緑になる。** 出たかどうかは `main` のコミットで確認する
